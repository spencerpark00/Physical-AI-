# D-008 로봇 시뮬레이션 — HPC 블레이드 검사

> 엔진을 분해했을 때 나오는 **블레이드(터빈 날개)를 로봇이 한 장씩 촬영해 검사 기록을 남기는 과정**을
> PyBullet(물리 시뮬레이터)으로 재현한 시연 코드.

**현재 대표본: [`sim_physical_ai.py`](sim_physical_ai.py)** · 시연 영상: [`demo_physical_ai.mp4`](demo_physical_ai.mp4) (43.8초)

---

## 1. 이 시뮬레이션이 보여주려는 것

### 한 줄로 말하면

> **"로봇이 시킨 대로 움직이는 것"과 "로봇이 보고 판단해서 움직이는 것"은 다르다.**

공장 자동화 로봇은 대부분 전자입니다. 좌표를 미리 넣어두고 그 위치로 갑니다.
물건이 조금이라도 어긋나 있으면 엉뚱한 곳을 찍고, 잘못 찍었는지도 모릅니다.

Physical AI는 후자입니다. **보고 → 판단하고 → 움직이고 → 결과를 확인하고 → 틀렸으면 다시 계획합니다.**
이 시뮬레이션은 그 다섯 단계가 말이 아니라 **실제 코드로 돌아간다**는 것을 보이기 위한 것입니다.

### 왜 하필 블레이드 검사인가

> **"1장은 사람이 더 빠릅니다. 그런데 엔진 한 대에 블레이드가 수백 장입니다."**

| 근거 | 내용 |
| --- | --- |
| 물량 | 오버홀 시 블레이드 **전수 검사**(입고 시 + 세척 후 2회). 대한항공 연 100대 → 360대 → 500대 목표 |
| 사람의 한계 | 육안 검사 정확도 **오염 상태 67% / 세척 후 87%**, 검사자에 따라 편차가 큼 (Aust & Pons, 현업 50명 대상) |
| 학술 결론 | **판정은 사람이 우수**, 기술의 강점은 **일관성·가용성·무편향성** → 촬영은 기계, 판정은 사람 |
| 업계 선례 | 루프트한자 AutoInspect: 연소기 라이너 검사 4교대 → 4시간 미만 |

> ⚠️ **KPI 주의**: "검사 시간 단축"을 대표 지표로 걸면 위험합니다. 1장만 놓고 보면 로봇이 더 느릴 수 있습니다.
> **증빙 완결률 · 검사자 간 편차 축소 · 판정 집중 시간 · 야간 일괄 처리량** 쪽으로 거는 것이 이 논리와 맞습니다.

## 2. 영상에서 무슨 일이 일어나는가

로봇은 두 부분입니다. 바닥을 굴러다니는 **이동 대차(Moby)** 위에 **로봇 팔(Indy7)**이 올라가 있습니다.
검사할 블레이드 4장이 바닥에 놓여 있고, 로봇이 한 장씩 찾아가 사진을 찍습니다.

```
작업지시 접수
     ↓
① 본다        위에서 한 장 찍어 블레이드가 어디에 어떤 각도로 놓였는지 알아낸다
     ↓
② 계산한다    "그 위치, 그 각도"에 맞춰 팔을 어떻게 뻗을지 푼다
     ↓
③ 이동한다    대차가 그 블레이드 앞으로 간다 (가는 길이 막혔으면 돌아간다)
     ↓
④ 찍는다      팔을 내려 블레이드 바로 위에서 촬영
     ↓
⑤ 자기 사진을 검사한다   블레이드가 화면에 제대로 담겼는지 부위별로 확인
     ↓
   합격 → 기록에 연결하고 다음 블레이드로
   불합격 → ⑥ 왜 실패했는지 판단 → ⑦ 자세를 바꿔 다시 촬영 → ⑤로
   2번 더 해도 안 되면 → 사람(정비사)에게 넘긴다
```

화면 왼쪽에 이 단계들이 한국어로 표시되고, 아래쪽 큰 띠에 **지금 로봇이 무슨 판단을 했는지**가 나옵니다.

### 색으로 보는 진행 상황

- **회색** = 검사 대기
- **청록** = 지금 작업 중
- **주황** = 촬영 실패, 다시 찍는 중
- **초록** = 검사 완료

## 3. 이 시뮬레이션의 두 가지 핵심 장면

### 장면 A — 블레이드가 사전 정보와 다른 곳에 놓여 있다

4장 모두 **일부러 조금씩 어긋나게** 놓았습니다. 위치는 최대 5cm, 각도는 최대 36°까지.

로봇은 이 값을 **모릅니다**. 위에서 사진을 한 장 찍어 블레이드의 윤곽을 잡아내고, 그 윤곽에서
중심 위치와 기울어진 각도를 계산합니다.

```
사전에 알던 위치   x=0.50  y=0.68  각도 0°
실제로 찍어보니    x=0.50  y=0.69  각도 +33.2°
                                    ↓
             카메라를 그 33.2°에 맞춰 정렬하고 팔을 뻗는다
```

**이게 진짜인지 확인하는 방법**: 검출한 각도를 넣었을 때와 0°로 뒀을 때 로봇 관절값이
**31.4° 차이**가 납니다. 화면에 각도만 띄우는 게 아니라, 그 값이 실제로 로봇을 다르게 움직입니다.

인식 정확도는 실제 위치 대비 **18~21mm, 각도 오차 0.3~2.3°**입니다.

### 장면 B — 3번 블레이드: 로봇이 스스로 두 번 다시 찍는다

3번 블레이드만 **받침대 위에 올려져 있습니다**. 정비 현장에서 흔한 상황입니다.

문제는 로봇이 사진 한 장으로는 **높이를 알 수 없다**는 것입니다. 사람도 한쪽 눈을 감으면
거리감이 떨어지는 것과 같습니다. 그래서 평소 높이로 촬영하는데, 블레이드가 그만큼 가까워져
있으니 사진에 다 안 들어옵니다.

```
1차 촬영   화면에 담긴 비율 70%
           팁 52%  루트 22%  외곽 엣지 72%   ← 부위별로 나눠서 본다
     ↓
   판단: "부품 전체가 화각보다 크다 = 너무 가까이서 찍었다"
     ↓
   → 촬영 높이를 0.50m에서 0.60m로 올린다

2차 촬영   화면에 담긴 비율 96%   ← 전체로는 합격 기준(90%)을 넘었다
           팁 84%  루트 95%  외곽 엣지 97%   ← 그런데 팁만 부족하다
     ↓
   판단: "팁이 부족하다. 그런데 반대편에 남은 여유가 0% 뿐이라 옆으로 옮길 수 없다"
     ↓
   → 다시 높이를 0.70m로 올린다

3차 촬영   화면에 담긴 비율 100%   팁 100%  루트 100%  엣지 100%   합격
```

**여기서 중요한 두 가지**

**하나.** 전체 평균이 96%로 합격 기준을 넘었는데도 불합격시켰습니다.
팁(날개 끝)에 생기는 균열은 팁이 안 찍히면 못 봅니다. **평균으로 덮으면 안 되는 값**이라
부위별 기준(88%)을 따로 뒀습니다.

**둘.** 2차 실패 때 "팁 쪽으로 카메라를 옮긴다"가 아니라 "옮길 공간이 없으니 거리를 띄운다"를
택했습니다. 로봇이 **화각에 남은 여유를 실제로 재보고** 결정한 것입니다.
(실제로 옮겨봤더니 팁은 84%→96%로 좋아졌지만 반대쪽 루트가 0%로 밀려났습니다. 개발 중 이 문제를
겪고 나서 여유를 재는 판단을 넣었습니다.)

나머지 3장은 1차 촬영에서 바로 통과합니다. 그래서 **재촬영이 "매번 하는 절차"가 아니라
결과가 나빴을 때만 로봇이 스스로 내리는 결정**이라는 게 대비로 드러납니다.

## 4. 실행 방법

```bash
cd C:\Users\User\robotsim

py -3.11 sim_physical_ai.py            # 3D 창으로 바로 보기 (Ctrl+드래그로 시점 회전)
py -3.11 sim_physical_ai.py --render   # 영상용 프레임 만들기 -> frames/*.png
py -3.11 make_mp4.py                   # 프레임 -> demo_physical_ai.mp4
```

**필요 환경**: Python **3.11** · `pybullet`(conda-forge) · `numpy` · `pillow` · `imageio-ffmpeg`

- pybullet은 Python 3.14용 사전빌드 wheel이 없어 3.11 + conda 설치를 사용합니다.
- `pillow`는 한국어 자막용입니다. 없으면 자막이 영문 비트맵 폰트로 대체됩니다(실행은 됩니다).
- ffmpeg 별도 설치 불필요 — `imageio-ffmpeg` 내장 바이너리를 씁니다.

**영상 규격**: 43.8초 · 1280×720 · 30fps · H.264 **Constrained Baseline** · 1.9MB
> Baseline 프로파일 = 재생 호환성 최대. High 프로파일은 일부 플레이어에서 재생이 막힙니다.

## 5. 발표에서 물어보면 정직하게 답해야 하는 것

시연이 실제보다 세 보이지 않도록, 한계를 미리 적어둡니다.

### 이건 "카메라로 본다"가 맞습니다

블레이드의 위치와 각도는 **시뮬레이터가 그린 화면의 픽셀에서** 계산합니다. 정답 좌표를 몰래
쓰지 않습니다. 코드의 `TRUE_POSE`(정답값)는 오차를 화면에 표시하는 용도로만 씁니다.

### 이건 학습된 AI가 아닙니다

- **신뢰도(92~98%)** 는 학습된 모델의 확신도가 아닙니다. 윤곽의 크기·길쭉한 정도·화면 가장자리에
  닿았는지로 만든 **품질 지표**입니다. "검출 품질 지표"라고 부르는 것이 정확합니다.
- 물체를 **종류별로 알아보는 것도 아닙니다**. 시뮬레이터가 알려주는 물체 구분 정보를 사용합니다.
  실제 현장에서는 이 자리에 학습된 세그멘테이션 모델이 들어갑니다.

### 장애물 회피는 "지도 기반 재계획"입니다

장애물 위치가 처음부터 정해져 있습니다. **주행 중에 센서로 새 장애물을 발견하는 것이 아닙니다.**
경로 계산(A\*)은 실제로 돌고, 대차도 실제로 좌우 20cm를 비켜 갑니다. 하지만 "돌발 장애물 감지"는
아직 아닙니다.

### 크기는 연출입니다

실제 HPC 블레이드는 수 cm이지만 화면에서 보이도록 **21.9cm로 확대**했습니다.
정밀 재현이 목적이 아니며, 물어보면 "흐름 가시화를 위한 연출 스케일"로 답하면 됩니다.

### 판정은 사람이 합니다

로봇은 **촬영과 기록까지**만 합니다. 결함이 있는지 없는지 판단하는 건 정비사입니다.
2번 재시도해도 제대로 못 찍으면 로봇은 멈추고 사람을 부릅니다(HITL).

## 6. 검증 결과

발표에서 "그냥 애니메이션 아니냐"는 질문에 쓸 수 있는 근거입니다.
아래 숫자는 전부 시뮬레이션을 돌려 **매 프레임 측정**한 값입니다.

| 항목 | 결과 |
| --- | --- |
| 블레이드 인식 정확도 | 실제 위치 대비 **18~21mm**, 각도 **0.3~2.3°** (4장 모두) |
| 인식 → 자세 연결 | 검출 각도 반영 시 관절값 **31.4° 차이** (고정 자세가 아님을 증명) |
| 팔 정렬 정확도 | 목표 대비 **0~3mm** |
| 닫힌 루프 | 3번 블레이드 **70% → 96% → 100%**, 원인 판단 2회, 3차에서 합격 |

## 7. 개발하며 막혔던 것들 — 같은 문제를 다시 만나면

같은 시간을 두 번 쓰지 않기 위한 기록입니다. 대부분 **"돌아가는 것처럼 보이는데 틀린"** 종류였습니다.

### ① IK가 엉뚱한 곳으로 팔을 보냈다 (14cm 오차)

PyBullet의 역기구학 함수는 목표를 **월드 좌표(방 전체 기준 좌표)** 로 받는데,
코드는 **로봇 기준 좌표**를 넘기고 있었습니다. 게다가 오차 보정은 반대 부호로 하고 있어서
두 실수가 서로를 가려, 첫 번째 블레이드만 우연히 맞았습니다.

> **교훈**: 4개 중 1개만 맞으면 "그 1개가 왜 맞았는지"를 의심해야 합니다.

### ② 정확히 조준했는데 사진에 30%밖에 안 담겼다

카메라 모형(더미 상자)이 로봇 손끝에 붙어 있었는데, 그게 **카메라 렌즈 바로 앞**이라
자기 몸이 시야를 가리고 있었습니다. 팔 자세에 따라 손목까지 끼어들어서 값이 30% / 3% / 52%로
들쭉날쭉했습니다.

→ 실제 장비처럼 **카메라를 손끝에서 6cm 앞으로 뺀 브래킷**에 다는 것으로 해결.

> **교훈**: 값이 규칙 없이 튀면 계산이 아니라 **가림(occlusion)** 을 의심합니다.

### ③ 잘려서 찍었는데 "100% 담김"으로 나왔다

"화면에 담긴 비율"을 **픽셀 수 비교**로 계산하고 있었습니다. 가까이서 찍으면 잘려도 픽셀 수는
오히려 늘어나기 때문에, 잘못 찍을수록 점수가 높아지는 구조였습니다.

→ **"부품 전체 윤곽 중 검사 화각 안에 들어온 비율"** 로 정의를 바꿨습니다.
넓은 화각으로 한 장 찍어 부품 전체를 확보하고, 그 안에서 실제 검사 화각에 들어온 부분을 셉니다.
거리·배율과 무관해집니다.

> **교훈**: 지표가 이상하면 계산 실수가 아니라 **정의가 틀렸을** 수 있습니다.

### ④ "충돌 0건"이 거짓이었다

대차가 장애물을 뚫고 지나가는데 충돌 검사는 0건을 보고했습니다.
PyBullet은 **움직이지 않는 물체(질량 0)끼리는 접촉을 계산하지 않습니다.** 대차도 장애물도 둘 다
질량 0이라 검사가 통과한 것입니다.

실제로 사각형으로 다시 재보니 **최대 13cm 관통**, 874프레임 중 851프레임에서 겹쳐 있었습니다.

원인은 경로 계획이 대차를 **원으로 근사**한 것이었습니다. 대차는 56×44cm 사각형인데 반지름 26cm
원으로 잡으니 실제 필요 간격보다 작았습니다.

→ 사각형 겹침으로 판정하도록 바꾸고, **씬을 만드는 시점에 검사**를 넣어
정차 위치가 장애물과 겹치면 아예 실행이 멈추게 했습니다.

> **교훈**: 검사 도구가 "이상 없음"이라고 하면, **그 도구가 그걸 볼 수 있는지**를 먼저 확인합니다.

### ⑤ 로봇이 덜덜 떨렸다

두 가지가 겹친 결과였습니다.
미리보기 화면이 물리 엔진을 매 프레임 돌리고 있었는데, ④의 겹침 때문에 접촉력이 팔을 밀고
다음 프레임에 강제로 되돌려지면서 30Hz로 진동한 것입니다.

→ 재생 화면에서는 물리 계산을 돌리지 않도록 하고, 겹침 자체를 없앴습니다.

### ⑥ 경로 재계획이 "말로만" 이뤄지고 있었다

화면에는 "장애물 → 우회 경로 생성"이라고 뜨는데, 대차는 직선으로 갔습니다.
두 개의 문제가 있었습니다.

- 여유 간격을 너무 크게 잡아 **목적지 칸이 사방으로 막혀** 경로 탐색이 실패했고,
  실패하면 **조용히 직선을 반환**하고 있었습니다.
- 재생 데이터가 대차의 **앞뒤 위치만 저장**해서, 좌우로 비켜 가는 움직임은 애초에 재생되지 않았습니다.

→ 실패 시 직선으로 위장하지 않도록 고치고, 좌우 위치도 저장하도록 바꿨습니다.

> **교훈**: **화면에 표시되는 것과 실제로 실행되는 것이 같은지**를 따로 확인해야 합니다.
> 이 프로젝트에서 가장 위험한 종류의 버그였습니다.

### ⑦ 재계획이 앞서 고친 것을 매번 되돌렸다

2차 촬영에서 높이를 올려 개선했는데, 3차 재계획이 **기본 자세를 기준으로** 다시 계산하는 바람에
그 높이를 잃었습니다.

→ **직전 자세에서 필요한 만큼만 더하는** 누적 방식으로 변경.

### ⑧ 그 외 환경 문제

- **한글 경로**: PyBullet이 한글이 포함된 경로의 파일을 못 엽니다 → 영문 경로(`C:\Users\User\robotsim`)로 복사해 사용
- **`np.linalg.eigh` 사용 시 프로세스가 그냥 죽음** → 2×2 행렬이라 공식으로 직접 계산
- **콘솔 인코딩**: `—`, `→` 같은 문자를 `print` 하면 한글 윈도우 콘솔에서 죽음 → ASCII로 대체
- **영상이 재생 안 됨**: H.264 High 프로파일이 일부 플레이어에서 막힘 → **Constrained Baseline**으로 재인코딩
